Multilingual Code-Smell Study

Do open-weight code models produce the code smell they are asked for, and does that depend on the language of the prompt or the programming language requested?

13 models, 22,152 files on prompt language · 5 models, 5,720 new files on programming language · source · data download

Summary

  1. Smell production falls from 54% in English to 44% in Chinese, the one prompt-language effect that survives every control.
  2. Both apparent validity effects belong to one model family. Spanish trails English (87.2% valid against 96.9%) because Granite leaves out the code fence in Spanish: accepting unfenced code takes granite-8b-code from 27% to 93%. C and C++ trail because granite-8b-code runs past the output limit.
  3. Code quality does not depend on the prompt language once broken files are set aside: 5.2 to 6.2 lint violations per 100 lines on parsing files in all four.
  4. The requested smell appears at the same rate in every programming language (72 to 74% of working files), but smell by smell the languages differ by up to 54 points, following each language's habits.

Where the validity gap comes from

The gap comes from 2 models; the other 11 are within 8 points of English in every language. In Spanish, Granite writes the word python on its own line instead of a fenced code block, and the extractor cannot separate the code from the prose around it:

Whether a dropped fence counts as a failure depends on whether following the requested format is part of the task. The scores on this page keep the stricter reading.

The C and C++ drop is one model. granite-8b-code writes valid C++ 43% and C 43% of the time, against 95% in Python, and 61% of its broken C++ and 84% of its broken C answers ran to the 2,048-token output limit and were cut off mid-statement. The other four models stay between 91.8 and 99.8% in every language. Separately, starcoder2-7b never stops by itself and reaches the cap on every answer in every language, but its code comes first, so it still parses 92 to 98% of the time.

Smells follow each language's habits

The flat average hides large differences smell by smell, and the direction is consistent: a smell is easier to produce where it is the ordinary way to write that language.

  • Data Class (Java 96.2%, Python 42.5%). A class of private fields with getters and setters is how Java ordinarily stores data, so a model writes a textbook example; Python has several competing conventions, so fewer answers match the definition.
  • Global State (C 97.4%, Java 69.2%). A variable at file level is ordinary C, while Java makes the model reach deliberately for a static field.
  • Long Parameter List (Python 100.0%, C 72.5%). C and C++ programmers usually pass a struct rather than many separate arguments.

How the numbers were produced

  • Generation. Oxford's ARC GPU cluster, one prompt at a time, greedy decoding, up to 2,048 new tokens, bfloat16 throughout. An answer is exactly reproducible on one machine; across GPU nodes a small share differ, enough to flip the parse verdict for about 7% of prompts in a CodeLlama comparison.
  • Prompts. Spanish, French and Chinese by NLLB-200 machine translation, with system prompts translated by hand. Java, C++ and C ported rather than translated, since "write a Python function" has to become "write a Java method"; 23 prompts were rewritten by hand.
  • Detectors. Experiment 1 uses the Python detector, 21 of 25 smells, built on Python's own parser. Experiment 2 uses one tree-sitter detector for all four languages, 12 of 25 smells, so each smell has a single definition; Python is re-scored with it so the four columns share an instrument.
  • Uncertainty. Intervals come from resampling whole prompts 500 times, because one prompt's files rise and fall together.
  • Excluded. mamba-codestral-7b substitutes a wrong token about once in every 140 and only 6 of 20 files parse. Five causes were tested: two were pipeline faults and were fixed, three were ruled out, leaving the published model itself. The release notes record what was tested.
